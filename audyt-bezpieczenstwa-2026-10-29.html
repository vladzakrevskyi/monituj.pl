1. Резюме для руководства

Общая оценка: хороший уровень безопасности. Критических и высоких уязвимостей не найдено. Есть 5 проблем среднего уровня. Самые важные: можно положить сервер одной картинкой размером ~190 КБ, и ключ шифрования документов лежит в тех же бэкапах, что и сами документы.

Обновление того же дня: M-01, M-04 и M-05 исправлены (подробности в карточках). Пункты M-02, M-03 и низкие остаются открытыми.

Разграничение данных между бюро и командами, обработка ссылок для клиентов, вход (пароль, Google, 2FA), платежи и вебхуки сделаны грамотно, на уровне выше среднего для SaaS этого размера.

4. Подробно: средний уровень

M-01Отказ в обслуживании через «фото страниц»

Средний · доступность
Где
apps/documents/pages.py:34–35 (_page)
Суть
Каждое фото страницы декодируется целиком (exif_transpose → convert("RGB")), и только потом уменьшается. Лимит пикселей (50 Мп) есть только для HEIC (validation.py:64). Для JPG и PNG его нет. Лимит Pillow по умолчанию — 178 Мп.
Проверено
PNG 13000×13000 весит 187 КБ. На его обработку уходит ≈ 880 МБ памяти и 2 секунды. В одном запросе может быть до 15 таких страниц.
Также
При исправлении нашлось то же самое для фото с iPhone (HEIC) в обычной загрузке: файл на 28 КБ — 770 МБ памяти.
Сценарий
Атакующий регистрируется или пользуется гостевой формой и отправляет prośbę сам себе. Затем по своей ссылке делает несколько параллельных запросов «Zrób zdjęcia stron». В продакшене 3 воркера gunicorn и нет лимита памяти для контейнера. Итог: OOM, перезапуск контейнера, сайт недоступен для всех. Повторять атаку можно сколько угодно.
Рекомендация
  • Проверять width × height сразу после Image.open: открытие ленивое, пиксели ещё не декодированы. Тот же лимит 50 Мп, что для HEIC.
  • Для JPEG вызывать image.draft("RGB", (2200, 2200)): декодирование сразу в уменьшенном размере, в 4–8 раз меньше памяти.
  • Глобально установить Image.MAX_IMAGE_PIXELS = 50_000_000.
  • Ошибки Pillow ловить и возвращать 400, а не 500.
  • В docker-compose.prod.yml задать mem_limit для web и worker и --max-requests для gunicorn.
Статус
Исправлено apps/documents/images.py:
  • размер проверяется по заголовку файла: JPEG до 300 Мп, PNG и HEIC до 50 Мп;
  • JPEG декодируется сразу уменьшенным: 200 Мп — около 90 МБ вместо 600+;
  • полное декодирование (HEIC, PNG) идёт по одному на весь сервер;
  • лимиты памяти контейнеров, --max-requests;
  • «бомба» из аудита теперь отклоняется за доли секунды, расходуя ~2 МБ памяти.

M-02Ключ шифрования лежит в тех же бэкапах, что и документы

Средний · конфиденциальность
Где
README «Krok 11» и строка 693; apps/documents/encryption.py:8–10; /srv/monituj/.env на сервере
Суть
Хостинг каждый день делает снимок всего сервера. В снимок попадают:
  • зашифрованные файлы;
  • база с обёрнутыми ключами файлов;
  • .env с DOCUMENTS_ENCRYPTION_KEY.
При этом README и комментарий в коде утверждают, что копия хостинга без ключа бесполезна и что ключа нет в бэкапах. Для бэкапов хостинга это не так.
Сценарий
Кто-то получает доступ к панели хостинга: украденный пароль, сотрудник провайдера, утечка у провайдера. Он восстанавливает снимок на свою машину и расшифровывает все документы всех клиентов. Шифрование «at rest» от этого сценария не защищает.
Рекомендация
  • Держать мастер-ключ вне диска, который попадает в снимок. Варианты: менеджер секретов (Doppler, 1Password Secrets Automation, HashiCorp Vault); подстановка при старте в tmpfs; как минимум — отдельный том, исключённый из снимков.
  • Включить 2FA и ограничение по IP в панели хостинга.
  • Исправить формулировки в README и, если они там есть, в Polityka prywatności и Umowa powierzenia, чтобы они точно описывали, от чего защищает шифрование.

M-03Бэкапы только у одного хостинга, без независимой копии

Средний · доступность
Где
README «Krok 11», deploy/deploy.sh (собственные дампы БД отключены)
Суть
Единственная копия данных — снимки у того же провайдера, хранятся 7 дней. Независимой копии у другого провайдера нет, тест восстановления не описан. Перед миграциями README только предлагает «убедиться, что последняя копия удалась».
Сценарий
Данные пропадают безвозвратно, если:
  • взломан или заблокирован аккаунт хостинга;
  • произошла ошибка или банкротство провайдера;
  • шифровальщик на сервере прожил больше 7 дней;
  • случайно восстановлен не тот снимок.
Для сервиса, которому бюро доверяют документы клиентов, это серьёзный бизнес-риск.
Рекомендация
  • Ежедневно делать pg_dump и архив тома storage. Шифровать отдельным ключом (age или gpg) и отправлять в хранилище другого провайдера с неизменяемостью (S3 Object Lock, Backblaze B2 с lock).
  • Раз в квартал проверять восстановление на чистой машине.
  • Срок хранения синхронизировать с LEGAL_BACKUP_DAYS.

M-04Фишинг от чужого имени через домен monituj.pl

Средний · злоупотребление и репутация
Где
templates/notifications/emails/zaproszenie_body.html, apps/requests/guest.py, apps/accounts/branding.py, лимиты в apps/requests/services.py:49–51
Суть
Отправить письмо с monituj.pl, которое проходит SPF и DKIM, может любой: бесплатная регистрация (до 5 в час с одного IP) или гостевая форма (1 в день с одного IP). В письме можно задать:
  • имя отправителя. Поправка: фильтр имён банков и учреждений в коде уже был (apps/accounts/sender.py), так что «mBank» не пройдёт. Но его обходили варианты написания: «mBank24», «m-bank», «Urz4d», кириллица. А имя при вступлении в команду не проверялось вовсе;
  • любой логотип (на триале тоже);
  • название и список документов, текст вопроса.
Новый аккаунт может отправить 50 писем в день, через 7 дней — 300.
Сценарий
Мошенник рассылает «prośby o dokumenty» от имени банка или налоговой. Люди загружают сканы паспорта и выписки, кнопка в письме ведёт на настоящий monituj.pl. Последствия:
  • прямой вред людям;
  • жалобы; домен попадает в спам-листы, и письма настоящих бюро перестают доходить;
  • риск по RODO как для оператора платформы.
Рекомендация
  • Запрещать в имени отправителя для новых и неоплаченных аккаунтов слова вроде urząd, skarbow, bank, ZUS, policja, KAS, PKO, mBank, ING.
  • Показывать логотип только после первой оплаты, не на триале.
  • Снизить лимиты, пока аккаунт не оплачен или не проверен.
  • Добавить в каждое приглашение ссылку «Zgłoś nadużycie» и мгновенно блокировать аккаунт при нескольких жалобах.
  • Следить за bounce и complaint rate у SMTP-провайдера.
Статус
Исправлено (по решениям владельца):
  • фильтр имён ловит обходы, проверяется и имя при вступлении в команду;
  • неоплаченные аккаунты не могут просить PIN, BLIK, SMS, CVV, номер карты или пароль к банку (content_rules.py);
  • в первую неделю без оплаты: 20 писем в день и не больше 20 получателей;
  • «Zgłoś nadużycie» в каждом письме клиенту и на его странице, с мгновенной тревогой без автоблокировки;
  • логотип на триале оставлен как есть — решение владельца;
  • мониторинг жалоб у SMTP-провайдера настраивается вне кода.

M-05Нет антивирусной проверки загружаемых файлов

Средний · целостность
Где
apps/documents/validation.py — проверка только расширения и MIME
Суть
Принимаются .doc и .xls (со старыми макросами), PDF (может содержать JavaScript и эксплойты), а также любой ZIP, переименованный в .docx или .xlsx: application/zip разрешён. Бухгалтер открывает эти файлы на рабочем компьютере, где лежат данные всех его клиентов.
Сценарий
Ссылка клиента пересылается или утекает. Кто-то посторонний загружает «Wyciąg bankowy.xls» с макросом. Файл попадает в панель бюро с пометкой «Dostarczony» и выглядит доверенным.
Рекомендация
  • ClamAV (clamd) отдельным контейнером: проверять файл до шифрования и сохранения, заражённые отклонять.
  • Для .doc и .xls показывать в панели предупреждение или вообще их отклонять.
  • Для .docx и .xlsx проверять наличие [Content_Types].xml, а не просто «это zip».
Статус
Исправлено apps/documents/antivirus.py:
  • ClamAV 1.5 в отдельном контейнере;
  • каждый файл проверяется до сохранения;
  • вирус — отказ и тревога;
  • файлы с макросами отклоняются;
  • подделанные .docx и .xlsx отклоняются;
  • если сканер недоступен, загрузка не принимается;
  • manage.py scan_documents проверяет старые файлы.
Серверу нужно 4 ГБ RAM.

5. Подробно: низкий уровень

L-012FA для администраторов не обязательна

Низкий
Где
apps/common/admin_security.py, deploy/env.production.example:81–83
Суть
Админка открывает все данные. Код из приложения она требует, только если у сотрудника 2FA уже включена. ADMIN_ALLOWED_IPS по умолчанию пуст, то есть ограничения нет. Блок location /admin/ в nginx закрывает только путь /admin/. Если сменить ADMIN_URL, админка становится доступна из интернета по одному паролю.
Рекомендация
Не пускать в админку is_staff без включённой 2FA. В продакшене не запускаться с пустым ADMIN_ALLOWED_IPS (fail closed).

L-02Медленный подбор 2FA и паролей ссылок

Низкий
Где
apps/accounts/two_factor.py (5 ошибок за 15 мин на аккаунт), apps/requests/services.py:52 (10 ошибок за 15 мин на IP и ссылку)
Суть
Лимит на аккаунт не растёт со временем. Если пароль уже известен, непрерывный подбор кода 2FA даёт ≈ 0,14 % успеха в сутки, ≈ 40 % за год. Пользователя о неудачных попытках не уведомляют: они видны только в ежедневном отчёте администратору. Лимит пароля к ссылке считается на каждый IP отдельно, поэтому ботнет его обходит.
Рекомендация
  • Прогрессивная блокировка: после 20 ошибок за сутки — блок на 24 ч и письмо владельцу аккаунта.
  • Для паролей ссылок — общий лимит на ссылку независимо от IP и минимальная длина пароля 10 символов.

L-03Токены и временные пароли в БД открытым текстом

Низкий
Где
Request.public_token, Request.confirmation_token, Request.pending_access_password (apps/requests/models.py:27, 42, 47); RecipientAccess.token; GuestAccess.token (apps/accounts/models.py:95); AgendaSettings.feed_token
Суть
Токены сброса пароля, подтверждения email, приглашений в команду и т. п. хранятся хэшами. А самые долгоживущие хранятся как есть:
  • ссылки клиентов;
  • постоянный вход в аккаунт без пароля (GuestAccess.token);
  • календарь;
  • пароль ссылки гостевой prośby — до 48 часов, пока prośba не подтверждена.
Утечка дампа или бэкапа БД даёт мгновенный доступ ко всем страницам клиентов и всем аккаунтам без пароля.
Рекомендация
Хранить SHA-256 токена, сам токен показывать только в письме. Ссылку клиента в панели собирать из отдельно зашифрованного значения (encryption.seal). Пароль гостевой prośby шифровать мастер-ключом.

L-04Секретные токены в журналах доступа

Низкий
Где
docker-compose.prod.yml:72 (--access-logfile -), журналы nginx, Cloudflare
Суть
Полные URL попадают в логи Docker и nginx: /d/<token>/, /dostep/<token>/, /moje-prosby/<token>/, /kalendarz/ics/<token>.ics, /reset-hasla/<token>/. Любой, у кого есть доступ к логам, получает доступ к документам и аккаунтам.
Рекомендация
Свой формат access-лога gunicorn и nginx с маскированием сегмента токена (/d/***/). Срок хранения логов не больше 14 дней.

L-05Гостевая форма пишет в чужой существующий аккаунт

Низкий
Где
apps/requests/guest.py:41–65 и submit
Суть
Атакующий указывает email зарегистрированного бюро как «свой» адрес отправителя. В аккаунте бюро сразу, до всякого подтверждения, появляется клиент с выбранными им именем и email и запись «Nowy klient» в активности. Бюро получает письмо с текстом атакующего. Через 48 ч всё это удаляется. Лимит — 1 раз в сутки с одного IP.
Рекомендация
Если аккаунт уже существует, до подтверждения ничего в нём не создавать: держать данные формы во временной таблице.

L-06Нет тайм-аута неактивности сессии

Низкий
Где
config/settings/base.py — SESSION_COOKIE_AGE не задан (по умолчанию 14 дней)
Суть
Панель с финансовыми документами остаётся открытой 2 недели, даже если ею не пользуются. Это риск для общих и офисных компьютеров. Кнопки «выйти со всех устройств» нет: сейчас это происходит только при смене пароля.
Рекомендация
Выход после 8–12 ч неактивности, абсолютный срок 7 дней (SESSION_SAVE_EVERY_REQUEST плюс своя проверка). В Ustawienia добавить «Wyloguj ze wszystkich urządzeń».

L-07CSP с Google Tag Manager на закрытых страницах

Низкий · глубина защиты
Где
apps/common/middleware.py (SecurityHeadersMiddleware), apps/common/analytics.py
Суть
GTM правильно грузится только на публичных страницах. Но заголовок CSP одинаков для всего сайта и разрешает https://www.googletagmanager.com и в панели, и на /d/<token>/. Такое разрешение — известный способ обойти CSP: атакующий подгружает свой контейнер GTM. Значит, если когда-нибудь появится XSS, CSP её не остановит.
Рекомендация
Для PRIVATE_PREFIXES отдавать строгую CSP без сторонних источников.

L-08Постоянная ссылка без пароля входит без нажатия кнопки

Низкий
Где
apps/accounts/views.py:844 (guest_access → _enter_guest_account)
Суть
Все остальные ссылки из писем требуют нажать кнопку: так почтовые сканеры не могут их «использовать». Постоянная ссылка аккаунта без пароля логинит сразу по GET. Корпоративные сканеры (Microsoft Safe Links, Mimecast) получают рабочую сессию в панели. Кроме того, подпись 14-дневной ссылки не скрывает данные: в ней видны id пользователя и первые 16 символов постоянного токена. Оставшейся энтропии достаточно, но так делать не стоит.
Рекомендация
Кнопка «Wejdź do panelu» (POST), как в остальных ссылках. В подписанной ссылке передавать HMAC от токена, а не его начало.

L-09Лимиты запросов не атомарны

Низкий
Где
apps/common/throttle.py:26–31
Суть
Сначала is_limited (COUNT), потом record (INSERT), без блокировки. При входе неудача записывается только после Argon2 (≈ 100 мс). Пачка параллельных запросов проходит проверку вся сразу, и лимит «8 попыток за 15 мин» реально становится в несколько раз больше.
Рекомендация
Атомарный счётчик: Redis INCR + EXPIRE, или select_for_update по ключу, или pg_advisory_xact_lock. Redis уже есть в стеке.

L-10Перечисление аккаунтов

Низкий
Где
RegistrationService.register («Konto z tym adresem email już istnieje»), смена email, приглашение в команду
Суть
Можно проверить, есть ли у бюро аккаунт в Monituj. Это помогает целевому фишингу (см. M-04). Сброс пароля, наоборот, сделан правильно и не выдаёт существование аккаунта.
Рекомендация
Отвечать на регистрацию одинаково: «sprawdź skrzynkę». Существующему пользователю отправлять письмо «ktoś próbował założyć konto na Twój adres».

6. Информационные замечания

IDЗамечаниеКомментарий
I-01/api/cookie-consent/ принимает POST без CSRF (apps/consents/views.py)Риск принят сознательно. Чужой сайт может добавить в журнал согласий бессмысленную анонимную запись (лимит 60 в час с IP). Ни данных, ни настроек пользователя это не меняет.
I-02Резервные коды 2FA (≈ 49 бит) и email-коды хэшируются SHA-256 без секретаПосле утечки БД резервные коды можно подобрать офлайн. Лучше HMAC с секретным ключом.
I-03Вебхук inFakt проверяет HMAC тела, но не времяПерехваченный запрос можно отправить повторно. Обработка идемпотентна (статус PROCESSING), поэтому ущерба нет.
I-04Ссылка «Pokaż wszystkie moje pliki» работает час и многократноПересланное письмо в течение часа даёт доступ ко всем файлам получателя. Можно сделать одноразовой.
I-05Подтверждение контактной формы повторяет имя (до 120 знаков) на любой адресМинимальная возможность для спама, лимит 5 в час с IP. Можно убрать имя из письма.
I-06SMTP вызывается синхронно в веб-запросе (EmailService.send)При медленном SMTP тормозят загрузки и вход, воркеры заняты. Лучше отправлять через Celery.

7. Что сделано хорошо

Изоляция данныхВсе объекты панели выбираются через request.account (get_owned_request, get_owned_client, фильтр по owner). IDOR не найден ни в одном из 150 маршрутов. Чужие id дают 404 без утечки информации.
Ссылки клиентов256-битные токены. Доступ привязан к сессии. Пересланная ссылка показывает только файлы, загруженные из этого браузера. Пароль хранится хэшем с лимитом попыток.
Шифрование файловAES-256-GCM, отдельный ключ на каждый файл, путь файла аутентифицирован, есть ротация мастер-ключа, в продакшене без ключа приложение не стартует.
АутентификацияArgon2. Лимиты по IP и по email. Сессия пересоздаётся при входе. Смена пароля и email подтверждаются письмом, старый адрес уведомляется. Опасные действия по ссылкам — только кнопкой.
2FATOTP с защитой от повторного использования шага, секрет зашифрован, коды одноразовые, «запомнить устройство» сбрасывается при смене пароля. Обязательна для всех способов входа.
Google OIDCPKCE, state и nonce. Подпись токена проверяется по ключам Google. Привязка по sub, не по email. Для не-Gmail адресов — подтверждение по email.
ПлатежиПодписи вебхуков Stripe и inFakt проверяются. Возврат из Checkout проверяет client_reference_id и customer. Живые ключи нельзя по ошибке поставить в режим sandbox.
XSS и заголовкиАвтоэкранирование везде. mark_safe только для своих данных. JSON-LD экранирован. В JS нет опасных innerHTML. Строгая CSP без inline, HSTS preload, DENY в iframe, nosniff.
ЗагрузкиБелый список расширений плюс сверка содержимого через libmagic. Случайные имена на диске. Квоты на файл, пункт и prośbę. Отдача только как attachment. HEIC перекодируется без метаданных.
ИнфраструктураКонтейнер не под root. БД и Redis не торчат наружу. gunicorn слушает только 127.0.0.1. nginx перезаписывает X-Forwarded-For. Реальный IP берётся только от Cloudflare.
МониторингЖурнал аудита, оповещения о входе в админку и смене прав, honeytoken-аккаунт (canary), ежедневный отчёт безопасности, отдельные серверные скрипты наблюдения.
ГигиенаСекретов в истории git нет. .env, storage и дампы в .gitignore. Зависимости без известных CVE. check --deploy чистый.
